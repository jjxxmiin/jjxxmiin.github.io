GPU를 여러 장 붙였는데 학습이 빨라지지 않는다면 **GPU 개수보다 데이터 공급 속도, 0번 GPU 집중, 프로세스별 batch·sampler 설정**을 먼저 확인해야 한다. 멀티 GPU는 자동으로 메모리와 시간을 모두 해결하는 기능이 아니라, 병렬 작업을 나누는 구조다.

## GPU가 기다린다면 DataLoader부터 본다

`num_workers`는 데이터를 불러오는 데 사용할 프로세스 수다. 원문이 참고한 [PyTorch forum 토의](https://discuss.pytorch.org/t/guidelines-for-assigning-num-workers-to-dataloader/813/4)에는 `GPU 수 × 4`가 실험상 좋았다는 경험칙이 소개된다.

```python
import torch

num_workers = 4 * torch.cuda.device_count()
```

하지만 이 값을 정답처럼 고정하면 안 된다. worker가 너무 적으면 GPU가 데이터를 기다리고, 너무 많으면 프로세스 생성과 메모리 사용의 overhead가 커질 수 있다. 실제 선택은 0부터 몇 단계씩 늘리면서 epoch 시간과 CPU·GPU 사용률을 비교하는 방식이 안전하다.

`pin_memory=True`는 CPU의 pinned memory를 이용해 host-to-device 전송을 준비한다.

![pin_memory](/assets/img/post_img/gpus/pin.png)

그림의 전송 구조는 [NVIDIA 설명](https://developer.nvidia.com/blog/how-optimize-data-transfers-cuda-cc/)에서 가져왔다. 데이터가 작거나 다른 구간이 병목이면 효과가 눈에 띄지 않을 수 있으므로 “True면 무조건 빠르다”가 아니라 실제 loader 대기 시간을 확인한다.

데이터 단계에서 기록할 값은 간단하다.

- batch를 받는 데 걸린 시간
- GPU 연산 한 step 시간
- worker 수를 바꿨을 때 전체 epoch 시간
- GPU마다 들어가는 실제 batch 크기

## AMP는 메모리를 줄이지만 검증이 필요하다

AMP(Automatic Mixed Precision)는 모든 연산을 32bit로 고정하지 않고 16bit 연산을 섞어 메모리와 연산 비용을 줄인다. 원문은 [Mixed Precision Training 논문](https://arxiv.org/abs/1710.03740)의 아이디어와 PyTorch 1.6부터 제공된 내장 기능을 사용했다.

![amp](/assets/img/post_img/gpus/amp.png)

```python
scaler = torch.cuda.amp.GradScaler()

for inputs, labels in loader:
    optimizer.zero_grad()

    with torch.cuda.amp.autocast():
        outputs = model(inputs)
        loss = criterion(outputs, labels)

    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()
```

이 코드는 model, loader, optimizer, criterion과 device 이동이 준비됐다는 전제의 **학습 loop 핵심 조각**이다. AMP를 켠 뒤에는 단순히 실행 여부만 보지 말고 다음을 비교한다.

- 같은 batch에서 loss가 정상적으로 감소하는가?
- 메모리가 실제로 얼마나 줄었는가?
- 줄어든 메모리로 batch를 늘렸다면 학습 조건도 함께 기록했는가?
- baseline과 최종 metric이 비슷한가?

속도가 좋아질 수 있다는 기대와 결과가 안정적이라는 검증은 별개다.

## DataParallel보다 DDP가 유리한 이유

`nn.DataParallel`은 한 프로세스 안에서 batch를 GPU별로 나누고 결과를 0번 GPU에 모은다.

```python
model = torch.nn.DataParallel(model)
```

사용은 간단하지만 큰 모델과 데이터에서는 0번 GPU에 작업이 몰리고 GPU 사이 불균형이 생길 수 있다. `DistributedDataParallel`(DDP)은 GPU마다 프로세스를 두고 동일한 모델로 각자 batch를 처리한다.

원문 전체 예제는 [pytorch_multi_gpu 저장소](https://github.com/jjxxmiin/pytorch_multi_gpu)에 있다. 아래는 구조를 읽기 위한 핵심 조각이며 dataset, model, optimizer, train 함수가 빠져 있어 완전한 실행 코드가 아니다.

```python
def main():
    world_size = torch.cuda.device_count()
    torch.multiprocessing.spawn(
        main_worker,
        nprocs=world_size,
        args=(world_size,),
    )


def main_worker(gpu, world_size):
    torch.distributed.init_process_group(
        backend='nccl',
        init_method='tcp://127.0.0.1:3456',
        world_size=world_size,
        rank=gpu,
    )

    torch.cuda.set_device(gpu)
    model = model.cuda(gpu)
    model = torch.nn.parallel.DistributedDataParallel(
        model, device_ids=[gpu]
    )

    sampler = torch.utils.data.distributed.DistributedSampler(
        train_dataset
    )
    loader = torch.utils.data.DataLoader(
        train_dataset,
        shuffle=False,
        sampler=sampler,
    )
```

`DistributedSampler`를 쓸 때 `shuffle=False`로 두는 이유는 DataLoader와 sampler가 동시에 순서를 섞지 않게 하기 위해서다. global batch를 GPU 수로 나눌지, GPU당 batch를 유지해 global batch를 키울지도 명확히 정해야 한다.

checkpoint는 0번 프로세스에서만 저장한다.

```python
if gpu == 0:
    save()
```

모든 프로세스가 동시에 같은 파일을 쓰면 손상되거나 서로 덮어쓸 수 있다. 반대로 load는 각 프로세스가 자신의 GPU 위치로 map해 같은 상태를 가져와야 한다. `dist.barrier()`는 모든 프로세스가 그 지점에 들어올 때까지 기다리므로, 위치를 잘못 잡으면 느림이나 멈춤처럼 보일 수 있다.

## “GPU 수만큼 빨라졌다”보다 먼저 확인할 것

멀티 GPU 성능은 GPU만의 숫자로 설명되지 않는다. 다음 순서로 한 단계씩 바꾸면 병목을 찾기 쉽다.

1. 단일 GPU에서 데이터 로딩 시간과 연산 시간을 분리한다.
2. AMP만 켜 메모리·시간·metric을 비교한다.
3. DDP에서 프로세스별 batch와 sampler가 겹치지 않는지 확인한다.
4. 0번 GPU 메모리와 사용률이 유독 높은지 본다.
5. checkpoint와 validation을 모든 프로세스가 중복 실행하는지 확인한다.

가장 큰 함정은 여러 최적화를 한 번에 켜고 빨라진 이유를 모르는 것이다. `num_workers`, pinned memory, AMP, DDP를 각각 측정해야 느려졌을 때 되돌릴 기준도 생긴다.
